## 2026-07-21: Repository State Is The Cross-Session Authority

### Decision

Use `PROJECT_STATE.md`, `DECISIONS.md`, and `ACTIVE_WORK.md` as the explicit
Session Bridge. Automatic memories and chat summaries are auxiliary only.

### Consequence

A result is not available to other sessions until it is written to a shared
file or committed and the other session re-reads that state. Every modifying
session must claim a bounded scope and complete a repository handoff.

## 2026-07-21: Zero-Update Loading Is Behaviorally Reproducible

### Evidence

The fixed 512-query zero-update regression produced zero differences in
embeddings, similarities, complete rankings, target ranks, and aggregate
retrieval metrics. The detailed classification is `KEY_ONLY_FAIL`.

### Decision

The legacy/current `inv_freq` key mismatch is not the cause of retrieval
degradation. The buffers are fixed and bitwise equal. The earlier Phase-3
degradation is attributable to training updates under the tested setup, not to
checkpoint loading alone.

### Do Not Repeat

- Do not keep investigating `inv_freq` as the primary root cause without new
  contradictory behavioral evidence.
- Do not describe `epoch0_best` as zero-update; it records epoch 0 after 256
  optimizer updates. The true zero-update reference is `phase2_baseline`.

### Decision

## 2026-07-21: Separate Phase-2 Initialization And Raw-Retrieval Roles

  checkpoint performance.

## 2026-07-21: First-Step Configuration Is Sound, But The Useful Window Ends Early

### Evidence

The first-step audit found zero optimizer membership errors, zero frozen or
temperature changes, no NaN/Inf, and no top-10 entry/exit after step 1. On the
same fixed ten-conformer evaluation, step 32 improved the balanced head metrics
while r2p Recall@10, p2r Recall@10, and p2r MRR fell by step 64.

### Decision

The durable result is `SHORT_USEFUL_WINDOW`, not `CONFIG_FAIL`,
`ONE_STEP_TOO_STRONG`, or `NO_ISSUE_FOUND`. Step 32 is a candidate cap that
must be reproduced on v3; it is not yet a production checkpoint.

### Do Not Repeat

- Do not reclassify the run as `NO_ISSUE_FOUND` merely because step 64 remains
  above step 0 on some metrics; the short-window definition compares the useful
  step with subsequent training.
- Do not promote a historical v2 step-32 checkpoint to the formal v3 result.
- Do not launch full-data or multi-epoch training before the bounded v3
  step-32 result is reviewed.

## 2026-07-21: A Formal v3 Step-32 Pilot Requires A Dedicated Bounded Contract

### Evidence

The completed first-optimizer-step audit used data version v2. Its script
hard-codes the historical v2 Pilot, evaluates through step 64, and saves only
step 0 and step 1 audit checkpoints. The current general training entry point
runs complete epochs and saves only at epoch boundaries. The current full and
multi-conformer evaluators select fixed historical checkpoint filenames and
model labels instead of an explicitly requested checkpoint.

### Decision

- Treat the v2 first-update audit only as historical diagnostic evidence.
- `phase3/drugclip/audit_first_optimizer_step.py` is not the runner for the
  formal v3 Pilot.
- A formal v3 bounded Pilot must execute exactly 32 successful
  `optimizer.step()` calls, save the resulting model as `step_032.pt`, and use
  an evaluator that explicitly selects and records that checkpoint.
- The bounded runner, checkpoint save/resume contract, explicit-checkpoint
  evaluator, and their tests must pass before any v3 Pilot is launched.

### Do Not Repeat

- Do not relabel v2 audit outputs or historical step checkpoints as a formal
  v3 Pilot.
- Do not approximate 32 steps with an epoch boundary or infer the evaluated
  model from `checkpoint_best.pt`/`checkpoint_last.pt` naming.
- Do not start training first and plan to repair the runner/evaluator contract
  afterward.

## 2026-07-21: Bounded Runner And Explicit Evaluator Gate Is Implemented

### Do Not Repeat

- Do not remove the strict v2/v3 checkpoint contract checks when selecting an
  explicit evaluator checkpoint.

dependency, v3 runtime contract, and bounded training/evaluator groups were

worktree at that HEAD passed all 68 Phase-3 tests, all 6 Phase-2 concat contract
tests, and the training, full-retrieval, and multi-conformer `--help` entry

### Decision

Treat A-E as a reproducible committed code baseline. The main worktree's
uncommitted Phase-2 queue changes, historical diagnostic sources, formal data,
checkpoints, runs, and other dirty content are not implicit dependencies of
the successful A-E code tests.

Git commits and clean-worktree tests prove code availability and test
reproducibility only. They do not prove that a real GPU Pilot, formal retrieval,
or ten-conformer evaluation has completed.

### Do Not Repeat

- Do not start the next experiment without a separate exact claim, explicit
  user authorization, and a new output directory.
- Do not treat the clean-worktree checkpoint hardlink as a committed artifact
  or evidence that training/evaluation ran.
- Do not expand training before the bounded v3 step-32 result is reviewed.
